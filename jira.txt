I reviewed the screenshots closely. The main point is: **your QA problem is not simply “the cluster needs more nodes.”** The cluster already has reasonable capacity, but the way workload requests, pod replicas, PDBs, and autoscaling interact is causing both **latency risk** and **scale-down restrictions**.

From your screenshots, the QA cluster `mics-qa-use4` is a **regional Standard GKE cluster in `us-east4`**, using an `n2-standard-16` node pool. Each node exposes roughly **15.89 allocatable vCPU and ~61.48 GB memory**. The node pool is configured with autoscaling at approximately **1–3 nodes per zone**, and because this is a regional pool across 3 zones, that can represent a materially larger total cluster size than the single-zone number suggests. GKE explicitly notes that multi-zone node pool sizing/autoscaling values can apply per zone depending on configuration, so this distinction matters before making any manual resize. ([Google Cloud Documentation][1])

The screenshots also show a very important clue: one node is **cordoned**, while several nodes have very different CPU requests. For example, some nodes are requesting around **9–10 CPU out of ~15.89 allocatable**, while another node is only around **0.5 CPU requested**. That means the issue is not simply “all nodes are full.” You have **uneven workload placement/resource reservation**, and probably a mix of pod requests that prevents Kubernetes from packing workloads efficiently.

The orange warning, **“Pod is blocking scale down because it doesn’t have enough Pod Disruption Budget (PDB)”**, is a separate issue from scale-up. It means GKE sees a node that could potentially be removed, but a pod on that node cannot be safely evicted because its PDB would be violated. PDBs are supposed to protect availability during voluntary disruptions, but overly strict PDBs can prevent the cluster autoscaler from consolidating nodes. ([Google Cloud Documentation][2])

So I would not recommend telling your lead, “We should just add 2 more nodes.” A more standard enterprise answer is:

**temporarily increase capacity for QA if immediate relief is required, but fix the workload autoscaling and resource configuration so the cluster scales automatically thereafter.**

### What I see in your QA cluster

Your current design already has **GKE Cluster Autoscaler enabled on the node pool**, because the screenshot shows `Autoscaling: 1–3 nodes per zone`. GKE's cluster autoscaler is specifically designed to add nodes when pods cannot be scheduled because of resource shortages, and remove nodes when capacity is no longer required. ([Google Cloud Documentation][3])

That means the first question should be:

**Why isn't the existing autoscaler solving the event-processing latency?**

The likely answer is that Kubernetes Cluster Autoscaler does **not** add nodes because an application is slow. It adds nodes primarily when pods need capacity and cannot be scheduled. So if you have six rule-execution pods running successfully but each pod is overloaded with requests, Kubernetes may still consider the cluster healthy.

That matches exactly what your team said:

> “Each rule itself is not taking time but the amount of requests it receives is huge. 1 plan event = 200+ rule executions.”

This sounds much more like a **horizontal application scaling problem** than purely a cluster capacity problem.

The correct relationship is:

```text
Incoming request spike
        ↓
Rule Execution pods consume CPU / custom metric increases
        ↓
HPA increases replicas
        ↓
Existing nodes fill up
        ↓
New pods become Pending if necessary
        ↓
GKE Cluster Autoscaler adds nodes
        ↓
New pods schedule on new nodes
```

That combination — **HPA + Cluster Autoscaler** — is the standard Kubernetes/GKE pattern. GKE recommends HPA for adjusting replica counts based on metrics and cluster autoscaler for resizing the underlying node pool. ([Google Cloud Documentation][4])

Right now you appear to have only the bottom part well configured.

# But this is the more important fix

Your rule-execution service needs an HPA.

You mentioned:

```text
Currently ~6 instances/pods
Very high request volume
1 plan event → 200+ executions
```

Suppose the workload currently looks roughly like:

```yaml
replicas: 6
```

Instead of manually changing that to 8, 10, or 12 whenever QA experiences load, introduce an HPA.

A typical starting point might look like:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: rule-execution-service
  namespace: mics-nonprod-qa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: rule-execution-service

  minReplicas: 6
  maxReplicas: 15

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Percent
          value: 100
          periodSeconds: 60

    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Percent
          value: 25
          periodSeconds: 60
```

Don't copy those exact thresholds directly into production. They should be tuned from actual load testing. But structurally, that is the pattern you want.

GKE supports HPA specifically for this use case. ([Google Cloud Documentation][5])

# Resource requests need review before adding nodes

The screenshots show that Kubernetes is scheduling based on **requested resources**, not necessarily actual consumption.

Run:

```bash
kubectl top pods -n mics-nonprod-qa --sort-by=cpu
```

and:

```bash
kubectl get pods -n mics-nonprod-qa \
  -o custom-columns="POD:.metadata.name,CPU_REQ:.spec.containers[*].resources.requests.cpu,CPU_LIMIT:.spec.containers[*].resources.limits.cpu,MEM_REQ:.spec.containers[*].resources.requests.memory,MEM_LIMIT:.spec.containers[*].resources.limits.memory"
```

For the specific rule service:

```bash
kubectl get deployment rule-execution-service \
  -n mics-nonprod-qa \
  -o yaml
```

Look for:

```yaml
resources:
  requests:
    cpu:
    memory:
  limits:
    cpu:
    memory:
```

This is crucial because Cluster Autoscaler makes scheduling decisions largely from **resource requests**, not from “the node looks busy in monitoring.”

If a pod requests:

```yaml
cpu: "4"
```

but normally consumes:

```text
700m
```

you are reserving almost 6× the CPU needed.

Conversely, if the pod requests:

```yaml
cpu: 250m
```

but routinely consumes:

```text
2 CPU
```

HPA behavior based on utilization can become misleading.

Google recommends right-sizing workload requests and limits and offers VPA recommendations for analyzing historical usage. ([Google Cloud Documentation][6])

For your situation, I would initially use VPA in recommendation mode rather than automatically allowing it to change the application.

Example:

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: rule-execution-vpa
  namespace: mics-nonprod-qa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: rule-execution-service

  updatePolicy:
    updateMode: "Off"
```

Then:

```bash
kubectl describe vpa rule-execution-vpa \
  -n mics-nonprod-qa
```

That gives you recommendations without letting VPA automatically restart/change the pods.

# Your PDB warning needs to be fixed separately

Check all QA PDBs:

```bash
kubectl get pdb -n mics-nonprod-qa
```

Then:

```bash
kubectl describe pdb -n mics-nonprod-qa
```

Look especially for cases such as:

```yaml
replicas: 1

PDB:
minAvailable: 1
```

That effectively tells Kubernetes:

> The only pod must always remain available.

Therefore it cannot be voluntarily evicted during node consolidation.

Another problematic example:

```text
replicas = 3
minAvailable = 3
```

Again:

```text
allowed disruptions = 0
```

For a stateless application with three or more replicas, something such as:

```yaml
spec:
  maxUnavailable: 1
```

is frequently easier to operate.

For example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: rule-execution-pdb
  namespace: mics-nonprod-qa
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: rule-execution-service
```

That maintains availability while still allowing node maintenance and scale-down.

The exact setting depends on the application's availability requirements; don't blindly relax PDBs just to clear the warning. Google's guidance is that PDBs should make workloads disruption-ready without unnecessarily preventing safe node operations. ([Google Cloud Documentation][2])

# Synchronous logging is also a legitimate concern

The other team member raised:

> “Logs are very high and they are synchronous.”

That could absolutely contribute to latency.

If your Spring Boot services are writing very high-volume INFO logs synchronously, every request may incur extra formatting, stdout/container logging and downstream ingestion overhead.

I wouldn't immediately change everything from `INFO` to `WARN`, though.

First identify noisy packages:

```bash
kubectl logs <pod> -n mics-nonprod-qa --since=5m | wc -l
```

and inspect application logging configuration.

If using Logback, async appenders are worth investigating.

Conceptually:

```text
Application thread
       |
       v
async logging queue
       |
       v
logging worker
       |
       v
stdout / logging backend
```

instead of:

```text
Application request
       |
       v
write log
       |
       v
wait
       |
       v
continue request processing
```

So the dev team's suggestion should be investigated alongside infrastructure scaling.

For MICS QA, I would aim for this architecture:

```text
                       ┌──────────────────────┐
                       │ Incoming Plan Event  │
                       └──────────┬───────────┘
                                  │
                              200+ rules
                                  │
                                  ▼
                    ┌─────────────────────────┐
                    │ Rule Execution Service  │
                    │                         │
                    │ Pods 6 → 8 → 12 → 15   │
                    └───────────┬─────────────┘
                                │
                         HPA monitors
                       CPU/custom metric
                                │
                 ┌──────────────┴──────────────┐
                 │                             │
          Capacity available             No capacity
                 │                             │
                 ▼                             ▼
          schedule pods            Cluster Autoscaler
                                             │
                                             ▼
                                 GKE adds node automatically
                                             │
                                             ▼
                                      pods scheduled
```

And on the way back down:

```text
Traffic decreases
      ↓
HPA reduces pod replicas
      ↓
nodes become underutilized
      ↓
PDB permits eviction
      ↓
Cluster Autoscaler removes extra node
```

That is much more sustainable than:

```text
latency → call DevOps → manually add 2 nodes
```

Yes. Your screenshot shows **AUTH = Enabled**, but the Console says **“Unable to load AUTH string.”** You can retrieve it directly with `gcloud`; Google documents `get-auth-string` specifically for this purpose. ([Google Cloud Documentation][1])

Your instance appears to be:

```text
mics-prod-redismem
```

and project:

```text
hcb-prod-mics
```

First determine the region if needed:

```powershell
gcloud redis instances describe mics-prod-redismem --project=hcb-prod-mics --region=us-east4
```

If it is `us-east4`, retrieve the AUTH string with:

```powershell
gcloud redis instances get-auth-string mics-prod-redismem --region=us-east4 --project=hcb-prod-mics
```

It should return something similar to:

```text
authString: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```

Google says the Memorystore AUTH string is automatically generated when AUTH is enabled and is unique to that Redis instance. ([Google Cloud Documentation][2])

### If you get PERMISSION_DENIED

That would also explain why the UI says **Unable to load AUTH string**. Your account may be able to view the Redis instance but **not retrieve its authentication credential**.

In that case, copy the exact permission error from:

```powershell
gcloud redis instances get-auth-string mics-prod-redismem --region=us-east4 --project=hcb-prod-mics
```

and we can identify the missing IAM permission/role.

Also, **don't disable and re-enable AUTH just to see the string**. Google states that re-enabling AUTH generates a new AUTH string, which would invalidate the existing credential for new connections and could break your PROD applications until their stored Redis secret is updated. ([Google Cloud Documentation][1])

Given the Redis connection failure you showed earlier, retrieving this value and securely comparing it with the Redis AUTH value currently supplied to your PROD application/Vault is a good next check.

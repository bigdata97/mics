This story is essentially about **removing the recipient list for the Daily ID Card Production Summary Report from hardcoded/application-deployment configuration and making it operationally manageable**.

The key sentence in the Jira story is:

> “As a MICS operations admin, I want to create and maintain a distribution list of email recipients, so that the Daily ID Card Production Summary Report is sent to the correct set of stakeholders without requiring a code change.”

So the story is **not mainly about sending the report**. The report generation/sending mechanism presumably already exists. The new capability is to **manage who receives that report**.

## What the story is asking you to achieve

Today, the application may be doing something like:

```java
List<String> recipients = List.of(
    "abc@cvshealth.com",
    "xyz@cvshealth.com"
);
```

or reading them from:

```yaml
report:
  recipients:
    - abc@cvshealth.com
    - xyz@cvshealth.com
```

or from a Kubernetes environment variable.

The problem with those approaches is that changing recipients typically means:

```text
Change code/config
      ↓
Create PR
      ↓
CI
      ↓
Deploy
      ↓
Restart/redeploy application
```

The story wants this instead:

```text
Operations Admin
       ↓
Add / Remove recipient
       ↓
Save configuration
       ↓
Next Daily Report Job
       ↓
Read latest recipient list
       ↓
Send report
```

**No service deployment should be needed just because somebody was added to or removed from the mailing list.**

# Acceptance criteria translated into technical requirements

Your screenshots have five important requirements.

### Create distribution list

An authorized operations user should be able to provide:

```text
user1@cvshealth.com
user2@cvshealth.com
user3@cvshealth.com
```

and save them.

The next report execution should automatically use those addresses.

### Update distribution list

An administrator should be able to:

```text
ADD:    user4@cvshealth.com

REMOVE: user2@cvshealth.com
```

without changing application code or redeploying the service.

### Validation

The system shouldn't allow:

```text
abc
abc@
@cvshealth.com
```

and ideally should reject duplicate entries such as:

```text
abc@cvshealth.com
abc@cvshealth.com
```

with an understandable error.

### Empty-list handling

This requirement is important.

If the list becomes empty, the scheduler should **not silently execute as though everything is fine**.

For example:

```text
Daily Report Job starts
      ↓
Recipient list = []
      ↓
Do NOT call email sender
      ↓
Log:
"No recipients configured for Daily ID Card Summary Report"
      ↓
Emit warning/metric/alert if required
```

This prevents people from thinking reports are being delivered when they aren't.

### Auditability

Every recipient modification should capture something like:

```text
Action: REMOVE
Recipient: user1@cvshealth.com
Changed by: eswara.reddy
Changed at: 2026-08-19T...
```

That gives operations/support a history of changes.

# How I would design this for MICS

For your current MICS architecture, I would **not put these email addresses in Vault**.

Vault is appropriate for:

```text
passwords
API credentials
MongoDB credentials
OAuth client secrets
tokens
certificates
```

A report recipient distribution list isn't secret data.

I'd use a persistent application configuration store, most likely **MongoDB**, assuming the application already uses MongoDB and there is no existing central configuration service.

The high-level architecture could be:

```text
                         ┌──────────────────────────┐
                         │ MICS Operations/Admin   │
                         └────────────┬─────────────┘
                                      │
                                      │ Add / Remove
                                      ▼
                         ┌──────────────────────────┐
                         │ Report Configuration API │
                         │                          │
                         │ Validate email           │
                         │ Prevent duplicates       │
                         │ Authorize admin          │
                         └────────────┬─────────────┘
                                      │
                                      ▼
                         ┌──────────────────────────┐
                         │ MongoDB                  │
                         │                          │
                         │ report_distribution_list│
                         └────────────┬─────────────┘
                                      │
                                      │ Read on every
                                      │ scheduled run
                                      ▼
┌──────────────┐          ┌──────────────────────────┐
│ Scheduler /  │─────────▶│ Daily ID Card Report Job │
│ Cron Job     │          └────────────┬─────────────┘
└──────────────┘                       │
                                      │
                                      ▼
                         ┌──────────────────────────┐
                         │ Existing Email Service   │
                         │ / Notification Service   │
                         └────────────┬─────────────┘
                                      │
                                      ▼
                         ┌──────────────────────────┐
                         │ Report recipients        │
                         └──────────────────────────┘
```

The critical design choice is:

**The scheduled report must read the recipient list dynamically at execution time.**

Don't load it only once during Spring Boot startup.

For example, avoid this kind of behavior:

```text
Pod starts
   ↓
Reads recipient list
   ↓
Keeps it in memory forever
```

because then a recipient change might still require a pod restart.

Instead:

```text
08:00 report runs
      ↓
query MongoDB
      ↓
get current recipients
      ↓
send

Next day 08:00
      ↓
query MongoDB again
```

That directly satisfies:

> reflected in the next report send, without any code deployment.

# Suggested data structure

You could keep this simple.

For example:

```json
{
  "reportName": "DAILY_ID_CARD_PRODUCTION_SUMMARY",
  "recipients": [
    "user1@cvshealth.com",
    "user2@cvshealth.com",
    "user3@cvshealth.com"
  ],
  "updatedBy": "madiree",
  "updatedAt": "2026-08-19T12:30:00Z"
}
```

And optionally maintain a separate audit collection:

```json
{
  "reportName": "DAILY_ID_CARD_PRODUCTION_SUMMARY",
  "action": "ADD",
  "recipient": "user3@cvshealth.com",
  "changedBy": "madiree",
  "changedAt": "2026-08-19T12:30:00Z"
}
```

That makes audit reporting much cleaner.

# Implementation in 3 logical steps

I would split this story into these three pieces.

### Step 1 — Externalize and persist the recipient configuration

Create a configurable recipient list outside application code.

For example:

```text
MongoDB collection:
report_configuration
```

Create:

```text
GET /report-config/daily-id-card/recipients

PUT /report-config/daily-id-card/recipients
```

or more granular APIs:

```text
POST   /report-config/daily-id-card/recipients
DELETE /report-config/daily-id-card/recipients/{email}
GET    /report-config/daily-id-card/recipients
```

The application should validate:

```text
valid email format
duplicate prevention
authorized administrator
```

This step satisfies:

```text
Create list
Update list
Validation
```

---

### Step 2 — Connect the Daily Report job to the dynamic list

Find where the existing report currently determines recipients.

It might look similar to:

```java
emailService.send(
    configuredRecipients,
    subject,
    report
);
```

Change the logic to:

```java
List<String> recipients =
        reportConfigRepository.getDailyReportRecipients();

if (recipients.isEmpty()) {
    log.warn("No recipients configured for Daily ID Card Production Summary Report");
    return;
}

emailService.send(recipients, subject, report);
```

The important point is that the list is retrieved **at report execution time**.

This satisfies:

```text
Next scheduled send uses latest list
No application deployment for recipient changes
Empty-list handling
```

---

### Step 3 — Add auditing and operational visibility

Whenever someone changes the list:

```text
ADD
REMOVE
REPLACE
```

record:

```text
who
what
when
```

Example:

```text
Distribution list updated
User       : madiree
Operation  : ADD
Recipient  : abc@cvshealth.com
Timestamp  : 2026-08-19T12:33:12Z
```

You can write that into:

```text
MongoDB audit collection

and/or

structured application logging
```

For stronger compliance, I prefer persistent audit history rather than relying solely on pod logs.

# Validation plan

I would validate the story with approximately these scenarios:

| Test                              | Expected result                               |
| --------------------------------- | --------------------------------------------- |
| Add valid email                   | Address saved                                 |
| Add multiple valid emails         | All saved                                     |
| Add malformed email               | Request rejected                              |
| Add duplicate email               | Duplicate rejected                            |
| Remove existing recipient         | Recipient removed                             |
| Change recipient list             | No application deployment/restart needed      |
| Run report                        | Latest list receives report                   |
| Add recipient before next run     | New recipient receives next report            |
| Remove recipient before next run  | Removed recipient doesn't receive next report |
| Empty list                        | Email isn't sent                              |
| Empty list                        | Warning/error logged                          |
| Update list                       | User + timestamp captured                     |
| Unauthorized user attempts update | Request rejected                              |

The most important end-to-end validation is:

```text
1. Start with:

A@cvshealth.com
B@cvshealth.com


2. Run report

A receives it
B receives it


3. Without deploying anything:

Remove A
Add C


4. Run report again

A does NOT receive it
B receives it
C receives it
```

If that works, you've proven the core requirement.

# What I would define as the outcome of the story

At the end of this story, these statements should all be true:

1. Recipient addresses are **not hardcoded** in the report implementation.
2. Authorized MICS operations users can add/remove recipients.
3. Changes require **no application code change or service deployment**.
4. The next scheduled report uses the latest configuration.
5. Invalid and duplicate addresses are prevented.
6. An empty list doesn't cause a silent successful report execution.
7. Distribution-list changes are auditable.
8. Existing Daily ID Card Summary Report behavior remains unchanged apart from recipient resolution.

# External dependencies you should identify before starting

This is the part I'd discuss early with your lead/developers because it determines your implementation.

**First: where does the current report run?**

Find the service/job that currently produces:

```text
Daily ID Card Production Summary Report
```

You need to know:

```text
service name
scheduler mechanism
email sending code
current recipient source
```

Without this, don't start designing the storage.

**Second: where should distribution-list configuration live?**

Confirm whether your team already has:

```text
MongoDB configuration collection
existing config API
operations/admin portal
existing report configuration mechanism
```

Reuse an existing mechanism rather than introducing a new database/API if one already exists.

**Third: email/notification service.**

Confirm the existing sender mechanism:

```text
Notification service?
SMTP?
internal CVS mail API?
another MICS service?
```

You shouldn't need to redesign email delivery for this story.

**Fourth: authorization.**

The acceptance criteria says:

> Given I have access to the report configuration

That implies some access control.

Determine:

```text
Who can modify distribution lists?

MICS Operations?
Admin role?
Support team?
```

If an admin UI/API already has authentication, reuse it.

**Fifth: auditing requirements.**

Clarify whether standard application logs satisfy "auditability", or whether the project requires persistent audit records.

I'd recommend explicitly asking:

> Do we need audit history persisted in the database, or is structured application logging sufficient for this story?

**Sixth: UI dependency.**

The story says "create and maintain", but doesn't explicitly say there must be a UI.

Clarify whether the expected interface is:

```text
Admin UI
REST API
database/config entry maintained operationally
```

This can change the story size considerably.

# Questions I would ask in grooming/refinement

There are a few ambiguities in the Jira story worth resolving before implementation:

* Where are the Daily Summary Report recipients currently configured?
* Is an admin UI expected, or is an API/configuration mechanism sufficient?
* Can any valid email domain be entered, or only `@cvshealth.com` / approved corporate addresses?
* Should at least one recipient always be required, or is an empty list intentionally supported?
* Who has permission to manage recipients?
* What audit retention is expected?
* Does changing the list need to take effect immediately or only before the next scheduled report?
* Do we need `To`, `CC`, and `BCC` groups separately, or only one recipient list?

That last one is especially useful to clarify now rather than discovering it during development.

## My recommended solution for this sprint

Assuming the existing MICS report service already has MongoDB connectivity, I would keep this story small:

```text
STEP 1
Create MongoDB-backed Daily Report recipient configuration
+ APIs to retrieve/update it
+ validation

              ↓

STEP 2
Modify existing Daily Report scheduler
to query current recipients immediately before sending

              ↓

STEP 3
Add auditing + empty-list warning
and perform end-to-end validation
```

I would **not introduce Kafka, Vault, a new GCP service, or a new microservice solely for this story** unless your current codebase already has a standard platform capability that requires it. This requirement is fundamentally a small persistent configuration-management capability layered onto the existing report process.
